# 阶段 5 实验报告：vLLM 接入与 32K 端到端

## 1. 结论

阶段 5 通过设计文档规定的出口条件：

- `oscar_mla_int2` 已接入 GLM‑5.2 原生 DSA/sparse MLA、三池 cache、
  scheduler metadata 和 worker allocation；
- 全新 Triton cache 的完整 A800 套件为 112/112 passed，26 项 CUDA 门禁
  全部实际执行；
- TP=8 服务完成短请求、506-token prefill、384-token 连续 decode、31,996-token
  近 32K 请求及 8 路并发请求，所有请求均为 HTTP 200；
- 最终日志证明 78 层均执行 OSCAR store、recent→INT2 demotion 和
  DSA-selected mixed read，且逐层计数完全一致；
- cache allocation 明确记录 `BF16 history=absent`，没有完整 BF16 latent
  history，也没有 dense/full-attention fallback；
- 同一实际 cache budget 下，latent-only 理论和 padding 后提升均为 6.4×，
  overall allocated capacity 提升为 3.5812365205×；实际分配与 planner 逐字节
  一致，满足第 10.3 节阈值。

大型模型、Triton cache、服务日志、请求响应和 metrics 仅保存在项目
`artifacts/phase5/`，没有提交或推送。

## 5. 三池显存与压缩率

正式 planner 的逐池结果如下：

| 分配项 | Slots/pages | Bytes | GiB |
| --- | ---: | ---: | ---: |
| BF16 prefix | 1,024 slots | 81,788,928 | 0.08 |
| BF16 recent | 4,096 slots | 327,155,712 | 0.30 |
| INT2 history | 637,696 slots / 9,964 pages | 7,958,446,080 | 7.41 |
| RoPE cache | — | 6,366,756,864 | 5.93 |
| 原生 DSA index/cache | — | 1,767,693,312 | 1.65 |
| 未使用尾差 | — | 459,060 | <0.001 |
| 总 budget | — | 16,502,299,956 | 15.3689644821 |

logical capacity 为 637,632 tokens。history 多分配的 64 slots 是独立 history
page namespace 的一个 page，不是可见 logical capacity，也不是完整 BF16
history。

对 78 层、512 维共享 latent：

- 纯 BF16 latent 为 `512 × 2 × 78 = 79,872 bytes/token`；
- INT2 data 为 `512 ÷ 4 × 78 = 9,984 bytes/token`；
- FP32 scale/zero metadata 为 `2 × 4 × 4 × 78 = 2,496 bytes/token`；
- INT2 history 合计为 12,480 bytes/token；
- latent-only 理论提升为 `79,872 ÷ 12,480 = 6.4×`；
- page padding 后提升仍为 6.4×；
- 把固定 prefix/recent、RoPE 和原生 DSA index/cache 一并计入后，同一
  16,502,299,956-byte budget 下的 overall allocated capacity 提升为
  3.5812365205×。

planner 实际 tensor allocation 合计为 16,501,840,896 bytes，与记录的各项 bytes
之和完全一致；余量为 459,060 bytes。因此“实际分配相对理论计算”的误差为 0%，
低于 5% 硬阈值。

阶段 1 原生运行的 capacity 为 165,696 tokens。本次观测比值为
`637,632 ÷ 165,696 = 3.8482039397450754×`，是同预算理论值的
107.45461568139605%，高于 95% 门槛。这个跨阶段比值不能解释为纯压缩率：
阶段 1 原生 cache budget 约为 14.3 GiB，而本次 OSCAR profile budget 为
15.3689644821 GiB；预算差异解释了它高于同预算 3.5812365205× 的现象。

## 6. OSCAR 路径与无 fallback 证据

全部 smoke 完成后的最后一条聚合日志为：

```text
layers=78, store=51246 (min=657 max=657),
demotion=23010 (min=295 max=295),
read=51246 (min=657 max=657)
```

三类计数均大于 0，且每类逐层 min=max；总数也分别等于
`78 × 657`、`78 × 295`、`78 × 657`。日志还明确记录：

- `OSCAR MLA three-pool write active; no full BF16 latent history`；
- `OSCAR MLA recent-to-INT2 demotion active`；
- `OSCAR MLA DSA-selected mixed prefix/recent/INT2 read active`；
- planner 的 `BF16 history=absent`。

成功服务日志中没有 `ERROR` 或 `Traceback`。A800 上
“DeepGEMM unsupported; using Triton fallback”仅指 sparse attention indexer
改用预期的 Triton 实现，不是 attention 退化到 dense/full attention；Gloo 的
hostname→loopback warning 也只涉及本机网络解析。

阶段 5 已完成。结果证明 OSCAR 三池在单机 8×A800、TP=8、原生
DSA/sparse MLA 和近 32K 请求下真实执行，并满足功能、无 fallback、无完整 BF16
history 及压缩率硬阈值。阶段 6 将把当前源码、依赖、native extensions 和 rotation

baseline OCI 作为最终候选身份。
